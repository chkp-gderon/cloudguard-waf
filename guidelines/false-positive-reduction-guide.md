# Check Point Web Application Firewall False Positive Reduction Guide

## Introduction

A Web Application Firewall (WAF) is most effective when it can accurately distinguish between legitimate application behavior and malicious activity. During the initial deployment phase, especially when protecting legacy, complex, or highly customized applications, false positives can occur as security engines learn the application's normal traffic patterns.

This document provides a practical framework for reducing false positives while maintaining a strong security posture. The objective is not to immediately eliminate every alert, but rather to systematically improve detection accuracy through traffic analysis, validation, tuning, and controlled enforcement.

By following the recommendations in this guide, organizations can:

- Accelerate the learning and optimization process.
- Improve the accuracy of behavioral and machine-learning based protections.
- Reduce operational overhead caused by false positive investigations.
- Maintain protection against known attacks during the tuning phase.
- Progressively move applications from monitoring mode to prevention mode with confidence.

The approach described in this guide is based on several core principles:

- Validate before whitelisting.
- Use trusted traffic to improve learning quality.
- Prioritize tuning efforts based on risk and severity.
- Introduce enforcement gradually.
- Continuously review and refine security models using real application traffic.

While every application environment is different, the methodology presented here can be applied to both modern and legacy applications and serves as a repeatable process for achieving high protection accuracy with minimal business impact.

## 1. Understand the Two Protection Layers

The WAF uses two complementary protection mechanisms:

- **Web IPS** protects against known web vulnerabilities and signatures.
- **Machine-learning WAF / Web Attacks** learns normal application behavior and detects anomalous requests.

These layers should be tuned separately. The machine-learning model needs representative traffic and time to learn, while Web IPS can generally be enforced earlier.

## 2. Put Web IPS in Prevent Mode Early

Enable **Web IPS in Prevent mode** as soon as the application is created, provided the event review does not reveal false positives.

Recommended validation:

1. Filter the events using `practicesubtype:"web ips"`.
2. Check whether Web IPS has generated any events.
3. If there are no events, or the observed events are confirmed as valid attacks, move Web IPS from **Detect** to **Prevent**.

Rationale:

- Web IPS protects against known vulnerabilities immediately.
- It has a very low false-positive rate.
- It provides protection while the machine-learning model is still learning.

## 3. Prioritize Event Review by Severity

Review detections in this order:

1. **Critical**
2. **High**
3. **Medium**

Resolve the critical false positives first before moving to lower severity levels. This makes the tuning process focused and allows enforcement to be introduced progressively.

## 4. Identify Top Sources of False Positives

Use the event filters to find which source IP addresses generate the largest share of detections.

For each top source:

1. Filter the event list by the source IP address.
2. Review all events generated by that source.
3. Determine whether the requests are legitimate application traffic.
4. Add the IP address as a trusted source only after validating its traffic.

The meeting example showed that a small number of source IP addresses generated most of the critical events, making them the logical starting point for investigation.

## 5. Use Trusted Sources to Improve Learning

A **trusted source is not a whitelist**.

Traffic from a trusted source:

- Receives a higher reputation score.
- Is used to teach the machine-learning model what normal behavior looks like.
- Can still be blocked if it sends requests that the model considers abnormal or previously unseen.

Only add a source after confirming that its observed requests are legitimate.

Enter trusted source IP addresses **one IP address per line**.

## 6. Temporarily Lower the Trusted-User Threshold During a POC

The normal trusted-user threshold requires the same behavior to be observed from **three individual trusted users or IP addresses** before it is considered trusted.

This protects the learning dataset against poisoning by a single trusted source.

During a controlled proof of concept, the threshold can temporarily be reduced:

- Change the threshold from **3 to 1** to accelerate learning when traffic volume is limited.
- Keep this setting only while the trusted traffic is being validated and the model is learning.
- Restore the threshold to **3** after false positives have reduced.

The production-safe setting remains 3 because it reduces the risk that one trusted source can poison the dataset.

## 7. Validate Whether an Event Is Legitimate

Use multiple indicators before classifying an event as benign.

### Application response

An **HTTP 200 response** indicates that the backend application understood and successfully processed the request. This is a useful sign that the request may be legitimate application behavior rather than simple probing, but it should still be validated in context.

### Developer confirmation

Confirm unusual application behavior with the development team. In the meeting, the developers had already confirmed that the unusual requests were part of how the legacy application was built.

### Event Advisor

Open **Event Advisor** for the event and review:

- Why the request was detected or blocked.
- The recommended next step.
- Whether the advisor says the legitimacy is unclear and should be verified.

If Event Advisor recommends verifying the intent with the development team, and the development team confirms the request is expected, treat that as evidence that the request is legitimate.

## 8. Mark Learning Suggestions as Benign

Review tuning suggestions in the asset's **Learn** area. A red indicator can signal that a tuning suggestion is available.

When a suggestion shows repeated detections for a URI that has been validated as legitimate:

1. Review the URI and associated events.
2. Confirm that the request behavior is expected.
3. Mark the suggestion as **Benign**.

This directly tells the machine-learning dataset that the observed behavior is normal. This action trains the dataset and does not require a separate policy enforcement action.

## 9. Introduce Machine-Learning Prevention Gradually

Do not wait for every learning stage to finish before introducing any machine-learning enforcement.

Recommended progression:

1. Keep the overall machine-learning policy in **Learn** while tuning false positives.
2. Enable **Prevent when score is Critical** once critical events have been reviewed and validated.
3. Continue training and resolving false positives.
4. Move to **High severity prevention** only after the model has learned enough legitimate traffic and high-severity events have been reviewed.

For a low-traffic test application with no critical detections, critical-severity prevention can be enabled earlier while the remaining learning continues.

## 10. Continue Feeding the Model Representative Traffic

After adding trusted sources or marking suggestions as benign, allow the system to observe more traffic.

The model needs:

- Time.
- Sufficient traffic volume.
- Validated examples of legitimate behavior.
- Feedback on incorrectly classified events.

False positives should decrease as the model sees repeated legitimate behavior from trusted sources and incorporates tuning feedback.

## Recommended Tuning Workflow

1. Review **Critical** events.
2. Identify the top source IP addresses generating those events.
3. Investigate all detections from each source.
4. Validate legitimacy using application responses, developer confirmation, and Event Advisor.
5. Add confirmed sources as trusted sources.
6. During a controlled POC, temporarily lower the trusted-user threshold from 3 to 1.
7. Mark validated learning suggestions as benign.
8. Check Web IPS events with `practicesubtype:"web ips"`.
9. Put Web IPS in Prevent mode when no false positives are found.
10. Enable machine-learning prevention for Critical severity first.
11. Continue monitoring and training.
12. Restore the trusted-user threshold to 3.
13. Move machine-learning prevention to High severity when false positives are under control.

## Key Principles

- A trusted source trains the model; it does not bypass protection.
- Validate traffic before marking it trusted or benign.
- Use Critical, High, and Medium severity as a phased tuning sequence.
- Keep known-attack protection active through Web IPS while machine learning matures.
- Reduce the trusted-user threshold only temporarily and in a controlled POC.
- Introduce prevention progressively instead of enabling all machine-learning enforcement at once.
- Better training data and explicit feedback are the main mechanisms for reducing false positives.
