# Check Point Web Application Firewall False Positive Reduction Guide

## Introduction

A Web Application Firewall (WAF) is most effective when it can accurately distinguish between legitimate application behavior and malicious activity. During the initial deployment phase, especially when protecting legacy, complex, or highly customized applications, false positives can occur as security engines learn the application's normal traffic patterns.

This document provides a practical framework for reducing false positives while maintaining a strong security posture. The objective is not to immediately eliminate every alert, but rather to systematically improve detection accuracy through traffic analysis, validation, tuning, and controlled enforcement.

By following the recommendations in this guide, organizations can:

- Accelerate the learning and optimization process.
- Improve the accuracy of behavioral and machine-learning based protections.
- Reduce operational overhead caused by false positive investigations.
- Maintain protection against known attacks during the tuning phase.
- Progressively move applications from monitoring mode to prevention mode with confidence.

The approach described in this guide is based on several core principles:

- Validate before whitelisting.
- Use trusted traffic to improve learning quality.
- Prioritize tuning efforts based on risk and severity.
- Introduce enforcement gradually.
- Continuously review and refine security models using real application traffic.

While every application environment is different, the methodology presented here can be applied to both modern and legacy applications and serves as a repeatable process for achieving high protection accuracy with minimal business impact.
## 1. Understand the Protection Layers

Treat the two protection mechanisms separately:

- **Web IPS** protects against known web vulnerabilities and attack signatures.
- **Machine-learning WAF**, sometimes shown as **Web Attacks**, learns normal application behavior and detects anomalous requests.

The machine-learning model requires representative traffic, validation feedback, and time to learn. Web IPS can generally be enforced earlier because it is focused on known attack patterns and typically has a low false-positive rate.

## 2. Enable Web IPS Prevention Early

Enable **Web IPS in Prevent mode** as soon as practical, provided that an event review does not reveal false positives.

Recommended validation process:

1. Filter the event logs for Web IPS events using:

   ```text
   practicesubtype:"web ips"
   ```

2. Review any returned events.
3. Confirm whether the events represent attacks or legitimate application behavior.
4. If no events are present, or all observed events are confirmed as valid attacks, move Web IPS from **Detect** to **Prevent**.

This provides immediate protection against known vulnerabilities while the machine-learning model continues to learn normal application behavior.

## 3. Review Events by Severity

Prioritize false-positive investigation in the following order:

1. **Critical**
2. **High**
3. **Medium**

Resolve critical false positives before moving to lower severity levels. This creates a controlled path toward enforcement and focuses effort on the detections that have the greatest impact.

## 4. Identify the Main Sources of False Positives

Use event filters and source statistics to identify the IP addresses responsible for the largest share of detections.

For each significant source:

1. Filter the event list by the source IP address.
2. Review the events generated by that source.
3. Determine whether the requests represent legitimate application behavior.
4. Add the IP address as a trusted source only after validating its traffic.

Starting with the highest-volume sources can reduce false positives efficiently because a small set of sources may account for a large portion of the detections.

## 5. Use Trusted Sources to Improve Learning

A **trusted source is not a whitelist**.

Traffic from a trusted source:

- Receives a higher reputation score.
- Contributes to the machine-learning model's understanding of normal behavior.
- Remains subject to inspection and can still be blocked when behavior is considered abnormal or has not been learned.

Only add a source after confirming that its observed requests are legitimate. Enter trusted source IP addresses **one IP address per line**.

## 6. Manage the Trusted-User Threshold Carefully

The trusted-user threshold controls how many individual trusted users or source IP addresses must exhibit the same behavior before the behavior is considered trusted for learning purposes.

### Recommended production setting

Use a threshold of **3** under normal production conditions. Requiring the same behavior from multiple trusted sources helps reduce the risk that one source can poison the learning dataset.

### Temporary POC setting

In a controlled proof of concept with limited traffic, the threshold can temporarily be reduced from **3 to 1** to accelerate learning.

Use this temporary setting only when:

- The trusted sources have been validated.
- Traffic volume is insufficient to satisfy the normal threshold quickly.
- The environment is actively monitored during the learning period.

Restore the threshold to **3** after false positives have decreased or sufficient training data has been collected.

## 7. Validate Whether Detected Traffic Is Legitimate

Use multiple indicators before classifying an event as benign.

### 7.1 Application response

An **HTTP 200 response** shows that the backend application understood and successfully processed the request. This can indicate legitimate application behavior rather than simple probing, but it should not be used as the only validation criterion.

### 7.2 Application-owner or developer confirmation

Confirm unusual request patterns with the application owner or development team. Legacy applications may use unusual URIs, parameters, payloads, or query structures that resemble attacks but are required by the application.

### 7.3 Event Advisor

Open **Event Advisor** for additional context and review:

- Why the request was detected or blocked.
- Which behavior or indicators triggered the detection.
- The recommended validation or remediation step.
- Whether the request's legitimacy is unclear and requires confirmation.

If Event Advisor recommends validating the request with the development team, use that confirmation as part of the decision. Do not exempt traffic solely because Event Advisor does not classify it as clearly malicious.

## 8. Mark Validated Learning Suggestions as Benign

Review tuning suggestions in the asset's **Learn** area. A visual indicator may show that a tuning suggestion is available.

When a suggestion contains repeated detections for a URI or behavior that has been validated as legitimate:

1. Review the URI and associated events.
2. Confirm that the behavior is expected.
3. Mark the suggestion as **Benign**.

This feedback teaches the machine-learning model that the observed behavior is normal. Because this updates the learning dataset rather than the policy configuration, it does not require a separate policy enforcement action.

## 9. Introduce Machine-Learning Prevention Gradually

Do not enable full machine-learning prevention before the application behavior has been sufficiently reviewed. Introduce prevention in phases.

Recommended progression:

1. Keep the overall machine-learning policy in **Learn** during initial tuning.
2. Review and resolve critical detections.
3. Enable **Prevent when score is Critical** when critical events have been validated.
4. Continue training the model and resolving false positives.
5. Review high-severity detections.
6. Extend prevention to **High** severity after legitimate high-severity behavior has been learned and false positives are under control.

For low-traffic applications with no critical detections, critical-severity prevention can be enabled while the remaining learning process continues.

## 10. Feed the Model Representative Traffic

The quality of machine-learning protection depends on the quality and variety of the traffic used during learning.

Ensure that the model receives:

- Representative legitimate user traffic.
- Traffic for important application workflows.
- Sufficient repetition of normal requests.
- Validated traffic from trusted sources.
- Explicit feedback on incorrectly classified events.

After adding trusted sources or marking suggestions as benign, allow the system to observe additional traffic so that the model can incorporate the changes.

## 11. Avoid Broad Whitelisting

Do not respond to false positives by broadly bypassing inspection for users, networks, URIs, or applications unless there is a specific and validated requirement.

Prefer the following sequence:

1. Investigate the event.
2. Confirm the expected application behavior.
3. Improve the learning dataset through trusted sources.
4. Mark validated tuning suggestions as benign.
5. Adjust enforcement by severity.
6. Use a narrowly scoped exception only when the behavior cannot be handled safely through learning or policy tuning.

Broad bypass rules reduce visibility and can create protection gaps.

## 12. Monitor the Effect of Tuning Changes

After each tuning change:

1. Observe new events from the affected source, URI, or workflow.
2. Confirm whether repeated false positives decrease.
3. Check that malicious or unexpected traffic remains detected.
4. Record temporary changes, including a trusted-user threshold of 1.
5. Revert temporary POC settings when their purpose has been achieved.
6. Expand prevention only after validating the previous enforcement stage.

Change one major tuning variable at a time when possible. This makes it easier to determine which adjustment affected detection behavior.

## Recommended Tuning Workflow

1. Confirm that the application is receiving representative traffic.
2. Review **Critical** events.
3. Identify the top source IP addresses generating those events.
4. Investigate the detections from each significant source.
5. Validate legitimacy using the application response, application-owner confirmation, and Event Advisor.
6. Add confirmed legitimate sources as trusted sources.
7. During a controlled POC, temporarily lower the trusted-user threshold from 3 to 1 if needed.
8. Review learning suggestions and mark validated behavior as benign.
9. Filter and review Web IPS events using `practicesubtype:"web ips"`.
10. Put Web IPS in Prevent mode when the review shows no false positives.
11. Enable machine-learning prevention for Critical severity.
12. Monitor the effect of the changes and continue training.
13. Restore the trusted-user threshold to 3.
14. Review High-severity events.
15. Extend machine-learning prevention to High severity when false positives are under control.
16. Continue periodic monitoring and investigate new application behavior when it appears.

## Decision Checklist for a Suspected False Positive

Before marking an event as benign or trusting its source, verify the following:

- [ ] The request belongs to an expected application workflow.
- [ ] The source identity or IP address has been validated.
- [ ] The application response is consistent with legitimate processing.
- [ ] The application owner or development team confirms the behavior when necessary.
- [ ] Event Advisor does not provide evidence that contradicts the benign classification.
- [ ] Related events from the same source have been reviewed.
- [ ] The proposed tuning action is narrower than a general whitelist.
- [ ] The effect of the change can be monitored.
- [ ] Any temporary threshold modification has a clear rollback condition.

## Key Principles

- A trusted source trains the model; it does not bypass protection.
- Validate traffic before marking it trusted or benign.
- Tune Critical, High, and Medium detections in phases.
- Keep known-attack protection active through Web IPS while machine learning matures.
- Lower the trusted-user threshold only temporarily and in a controlled environment.
- Restore production-safe settings after the accelerated learning period.
- Introduce prevention progressively instead of enabling all enforcement at once.
- Prefer learning feedback and narrowly scoped tuning over broad whitelisting.
- Better training data and explicit validation feedback are the main mechanisms for reducing false positives.
